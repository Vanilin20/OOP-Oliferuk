# Самостійна робота №2: Процедурний і об'єктний підходи

## 1. Незручності процедурного підходу
1. **Розкиданість даних:** Інформація про один товар зберігається в трьох різних масивах (`names`, `prices`, `quantities`). При зміні елементів легко переплутати індекси.
2. **Відсутність цілісності даних:** Немає гарантії, що всі масиви мають однакову довжину. Додавання ціни без назви призведе до помилки `IndexOutOfRangeException`.
3. **Важкість розширення:** Логіка обчислення знижки прив'язана до конкретних масивів і її важко використати в іншому місці програми.

---

## 2. Порівняння процедурного та об'єктного підходів

| Критерій | Процедурний підхід | Об'єктно-орієнтований підхід |
| :--- | :--- | :--- |
| **Структура даних** | Дані розбиті по окремих масивах | Дані та логіка об'єднані в об'єкти (`Product`, `CartItem`, `Cart`) |
| **Додавання операції** | Потрібно переписати функції під усі масиви | Достатньо додати новий метод у клас `Cart` |
| **Повторне використання** | Важке, код прив'язаний до масивів | Легке, клас `Cart` можна перевикористати |
| **Надійність** | Низька (легко розсинхронізувати) | Висока (дані захищені інкапсуляцією) |

---

## 3. Відповіді на контрольні запитання
1. **Незручності процедурного підходу:** Складність контролю синхронності кількох масивів і передача великої кількості параметрів у методи.
2. **Чому логіка знижки природніша в Cart:** Знижка є бізнес-правилом обробки кошика, тому вона має описуватися всередині об'єкта, який контролює товари.
3. **Що стало легше змінити після переходу на класи:** Легше додавати нові властивості товару та розширювати функціонал кошика без зміни зовнішнього коду.
4. **Коли процедурний підхід виправданий:** У невеликих скриптах, одноразових утилітах або простих математичних обчисленнях.
